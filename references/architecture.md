# 架构：把值钱的东西移出客户端

客户端加固只能拖延时间。下面这些调整让"读懂客户端"本身失去价值，优先级最高。

## 核心逻辑放服务端

- 算法、推荐与排序、定价、风控规则、模型推理、付费内容的生成，都做成 API，客户端只拿结果。
- 判断标准：竞争对手完整拿到这段代码会造成损失，它就不该放在客户端。
- 必须在本地运行的逻辑（离线功能、低延迟交互），尽量把规则和参数留在服务端按需下发，并接受本地那部分终会被看到。

## 客户端不放秘密

- 第三方服务的 API Key、签名私钥、数据库连接串、对象存储凭证、内部管理地址，都不进客户端。
- 调用第三方服务走自己的后端代理，由后端持有密钥并负责限流。
- 用户级凭证由后端签发，保持短期有效、权限最小。
- 前端构建会把特定前缀的环境变量原样写进产物：`VITE_*`、`NEXT_PUBLIC_*`、`REACT_APP_*`、`EXPO_PUBLIC_*`。只有确认可以公开的值才能使用这些前缀。
- 发布过的密钥按已泄露处理，立即轮换。

## 权限和付费由服务端判定

- 每个接口独立校验身份和权限，不依赖前端隐藏按钮或路由守卫。
- 付费功能由服务端只对付费用户返回内容或能力。客户端里的 `isPro`、`isVip` 之类的开关可以被直接修改。
- 软件授权以服务端在线校验为主，离线校验只作补充。

## 未发布和内部功能不进包

- 未上线的功能用服务端开关控制，或在构建时裁剪掉，不要只靠客户端 feature flag 隐藏。
- 管理后台单独构建、单独部署，登录后才下发，不和用户端打进同一个 bundle。懒加载的 chunk 同样可以被直接下载。

## 接口按会被直接调用来设计

- 攻击者可以绕过界面直接调用接口，因此需要限流、配额、异常检测和 bot 防护。
- 客户端请求签名只能增加摩擦，因为签名密钥本身就在客户端里。
- 返回字段按页面需要裁剪（DTO 或字段白名单）。整行数据库记录、内部 ID、成本价、其他用户的信息都不该出现在响应里。
- GraphQL 在生产环境关闭 introspection 有一定帮助，真正起作用的是字段级鉴权。

## 服务端不信任客户端上报的值

- 价格、分数、权限、时间、余额等关键值一律在服务端重新计算或校验。客户端可能已被修改，也可能被完全重写。
